## Block 1 — 单机核心（8/5 周三 – 8/9 周日，5 天，22h）

目标：单节点能按时触发、失败会重试、重启不丢。

### 8/5 周三 — 骨架与 schema

- 建仓库，从 B 复制 CI、docker-compose、Makefile
- `tasks` 表：`id, idempotency_key, payload, callback_url, fire_at, state, version, shard, lease_owner, lease_expires_at, attempt_count, created_at, updated_at`
- **核心索引 `(shard, state, fire_at)`** —— 轮询方案下这个索引就是性能本身，建错了后面压测直接崩
- `shard` 在插入时算好写死，不要查询时算
- Flyway 迁移接入

**验收**：`docker compose up` 起 PG，迁移执行成功，`EXPLAIN` 确认轮询查询走索引。

### 8/6 周四 — 提交与查询 API

- `POST /tasks`、`GET /tasks/{id}`
- 提交侧幂等：唯一约束冲突时返回已存在的任务
- 校验：`fireAt` 在未来，范围 1 秒 – 30 天

**验收**：同一 `idempotencyKey` 提交两次，库里一条记录，两次返回同一 `taskId`。

### 8/7 周五 — 轮询与 claim 循环

今天是替代时间轮的那一天，也是全项目最该写对的一段 SQL。

- 200ms 周期轮询，`UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 500) RETURNING *`
- **从今天起所有取时间的地方注入 `java.time.Clock`**，不要直接调 `Instant.now()`。成本 20 分钟，8/23 的时钟场景全靠它，而且单测也好写
- 空转时必须廉价：没有到期任务时是一次有界索引扫描
- claim 到的任务交给固定大小的线程池执行

**验收**：灌 10 万 pending 任务，轮询循环 CPU 占用可忽略；`fire_at` 到点后 200ms 内被 claim。

### 8/8 周六 — HttpSink、状态流转、triggerId

- `TaskSink` 接口 + `HttpSink`，超时 **10 秒**（严格小于租约 TTL 30 秒）
- `pending → firing → succeeded` 落库
- **`triggerId` 由 `taskId` 确定性推导**，同一任务所有尝试保持不变
- attempt 次数放在单独 header，只做观测，不参与去重
- 写测试用 receiver（带「按概率返回 500」和「按 triggerId 去重」两个开关）

**验收**：端到端跑通；人为让同一任务触发两次，receiver 靠 triggerId 去重，业务只执行一次。

### 8/9 周日 — 重试、死信、reaper

- 指数退避，最多 5 次，`retrying` 落库，耗尽进 `dead`
- **reaper**：扫描 `state='firing' AND lease_expires_at < now()` 的行，退回 `pending`
- reaper 是「假死不丢任务」的机制基础，今天必须写完，别拖到 Block 2

**验收**：场景 2 可复现；手工把某行的 `lease_expires_at` 改到过去，reaper 在 10 秒内回收它。

## Block 2 — 分布式化（8/10 周一 – 8/14 周五，5 天，22h）

**项目命根。** 8/14 是搬家前最后一个工作日，必须留作 buffer。

### 8/10 周一 — shard 表与分配策略

- `shards` 表：`shard_id, lease_owner, lease_expires_at, version`，64 行
- 启动时贪心抢占 lease 为空或已过期的 shard，软上限 `ceil(64 / 活跃节点数)`
- 节点只轮询自己持有的 shard

**验收**：起 2 个节点，64 个 shard 大致均分，各自只 claim 自己分片内的任务。

### 8/11 周二 — 租约续期与过期接管

- 心跳每 10s 续约，TTL 30s
- 续约失败 → 立即停止轮询该 shard，不再触发其中任务
- 其他节点扫描过期 shard 并抢占

**验收**：场景 1 —— `docker kill` 节点 A，节点 B 在 10 秒内接管其 shard 并继续触发。

### 8/12 周三 — 去重计数与竞态验证

- 埋点 `duplicate_trigger_total`（receiver 侧按 triggerId 判定）
- 构造「A 仍持有 shard 认知、但 shard 已被 B 接管」的场景，验证 7.1 的条件更新让 A 影响 0 行
- 埋点 `lease_takeover_total`

**验收**：两节点同时尝试触发同一任务，只有一个成功进 `firing`。

### 8/13 周四 — 取消/改期 + Testcontainers

- `DELETE` / `PATCH`，乐观锁 `version`，非 `pending` 返回 409
- 改期在轮询方案下就是一条 `UPDATE fire_at`，成本接近零
- Testcontainers 夹具：PG + Redis + 多实例应用
- 把 8/11–8/12 的场景固化成自动化用例

**验收**：`./gradlew test` 一条命令，分布式用例全绿。

### 8/14 周五 — buffer + 收尾

补账、提交、推送。写一份「当前进度 / 待办 / 已知问题」笔记——接下来 3 天你会完全断开。

## Block 4 — 混沌演练（8/18 周二 – 8/23 周日，6 天，30h）

### 8/20 周四（6h）— 场景 1、2 脚本化

杀节点接管、下游持续 500 进死信。两个都要有可重复的脚本和一致性报告。

### 8/21 周五（6h）— 场景 6：节点假死双发 ★

**这是全项目对求职结果贡献最大的一天。**

脚本流程：

1. 提交任务，节点 A claim，进入 `firing`
2. `kill -STOP` 冻结 A（模拟长 GC / 宿主机卡死）
3. 等待 30 秒，任务级租约过期
4. reaper 把任务退回 `pending`，节点 B claim 并触发，用**相同的** triggerId
5. `kill -CONT` 唤醒 A，A 的 HTTP 调用继续完成，也发出去了
6. Grafana 上 `duplicate_trigger_total` +1
7. receiver 按 triggerId 去重，业务动作仍只执行一次

**验收**：整个流程一条脚本跑完，一致性报告显示「重复触发 1 次，业务执行 1 次，任务丢失 0」。这份报告 + 那张 Grafana 截图，就是简历上最硬的那块。

### 8/22 周六（6h）— 场景 3、4、5

重复提交去重、取消与触发竞态、网络分区（分区节点失去 shard，恢复后主动放弃而非继续触发）。

### 8/23 周日（6h）— 场景 7、8 + 全部进 CI

**场景 7 — 时钟偏移**：`Clock.offset` 把某节点拨快 5 分钟。验证触发行为不变（因为判定都在 PG 侧），并**确认 `trigger_delay_seconds` 是用数据库时钟算的**——如果它用的是节点本地时钟，那么 README 首页那张精度直方图在任何时钟偏了的机器上都是假数字。这一条必须实测。

**场景 8 — 时钟漂移**：自写 `DriftingClock`，把某节点走速调到 1/3。预期观察到两件事：心跳每 30 秒真实时间才续一次约、shard 反复丢失又抢回；10 秒的 sink 超时变成 30 秒墙上时间、突破租约 TTL 造成双发。**找出设计崩溃的漂移系数临界值并写进 ADR-005。**

八个场景全部在 CI 跑绿。
